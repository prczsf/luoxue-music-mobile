# ADR 0004: 下载文件命名与重复下载语义

## Status
Accepted

## Context
下载能力本次要接线 `download.fileName` 设置（`歌名 - 歌手` / `歌手 - 歌名` / `歌名`），并新增批量下载入口。两个问题必须先定死，否则会产出用户磁盘上不可逆的脏数据：

1. 文件名里要不要带音质后缀（旧行为是非 128k 追加 `[320k]`）？
2. 批量下载时，如何判定"这首歌是否已经在磁盘上了"？

第 2 问的难点在于：本次同时决定**已完成任务不持久化**（见 [ADR 0005](0005-download-queue-persistence-and-recovery.md)），因此不存在 `歌曲 id ↔ 文件` 的映射表。而 [ADR 0002](0002-my-download-page-and-playback.md) 已确立「我的下载」以磁盘为唯一真相。

## Decision

### 1. 命名
- 基础名 = `filterFileName(formatMusicName(setting['download.fileName'], name, singer))`；结果为空时退回 `musicInfo.id`。
- **不追加音质后缀**，扩展名由下载流的**真实容器**（文件头魔术字）决定。
- 伴生文件（`.lrc` / `.jpg`）与音频完全同名，仅扩展名不同。

### 2. 重复下载语义
- **单曲下载**：目标同名文件已存在 → `unlink` 后写入（静默覆盖）。
- **批量下载**：入队前扫描一次下载目录，存在同名基础文件（`.mp3/.flac/.m4a/.ogg/.wav/.ape` 任一）即跳过，并在汇总提示里报告跳过数。
- **不做按歌曲 id 判定"已下载"**，也不引入已完成台账。

## Considered Options

- **保留音质后缀**（旧行为）：同一首歌 128k/320k 各留一份 → 磁盘重复、播放器列表出现多份同名歌；用户明确否决。
- **批量时逐首询问是否覆盖**：批量场景下弹窗会淹没用户。
- **批量时一律静默覆盖**：整套歌单重下会全量重下，浪费流量与时间，而多数歌本来就有。
- **引入"已完成任务"持久化台账按 id 判定**：与 ADR 0002「磁盘是唯一真相」冲突；且用户手动删除/移动文件后台账必然失真，等于新造一类不一致来源。

## Consequences

- 同一首歌在磁盘上只保留一份音频；换音质靠单曲重下（覆盖），批量重下不会刷新音质。
- 批量跳过是**按文件名的近似判定**：不同曲但同名的歌（翻唱、同名作品）会被误判为已存在而跳过——单曲下载不受影响，可手动下。
- 用户改动 `download.fileName` 设置后，历史文件不再命中跳过判定（按新名字看就是不存在），会多出一份不同名的文件。这是刻意接受的行为：改名设置本就是"以后按新规则来"。
