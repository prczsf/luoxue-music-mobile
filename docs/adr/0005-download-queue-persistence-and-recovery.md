# ADR 0005: 下载队列的持久化与恢复语义

## Status
Accepted

## Context
下载从"单曲即时任务"改为 FIFO 队列（并发上限可配，默认 3），因为要支持批量下载入口与进度可见。移动端一次批量下载可能持续几分钟到几十分钟，App 很容易被系统回收，而 RNFS 的下载任务**没有断点续传能力**（暂停等于重下）。因此必须回答：队列状态存哪、重启后怎么续。

## Decision

### 1. 持久化范围
- 任务结构复用既有 `LX.Download.ListItem`（`status: run/waiting/pause/error/completed`）。
- **只持久化未完成任务**：`waiting` 原样、`run` 重启后回落为 `waiting`、`error` 保留（等用户重试或清除）。
- **已完成任务不持久化**：其产物就是磁盘上的文件，「我的下载」页扫目录即可见（[ADR 0002](0002-my-download-page-and-playback.md)），不需要第二份会膨胀且会失真的记录。

### 2. 恢复语义
- 恢复时**丢弃持久化的 URL 与进度**，用 `musicInfo + quality` 重新走音质协商与跨源兜底。
- 不实现暂停与断点续传；恢复一律从头下载，缓存目录里残留的 `tmp` 文件一律删除。
- 恢复前做一次前置检查（存储权限 + 下载目录可写）：不可用则**整批置 `error`** 并只给一条明确提示，等用户处理后再手动重试；不静默失败、也不逐条刷屏。
- 恢复后的并发数读**当前**设置值，而非任务入队时的历史值。

## Considered Options

- **纯内存队列**：实现最省事，但用户排几十首后被系统回收即全部消失，体验等于"批量下载不可用"。
- **复用持久化的 URL 继续下载**：音源 URL 带时效与防盗链，几分钟后必然 403，成功率极低且失败原因隐蔽。
- **持久化已完成任务作为下载历史**：与磁盘扫描重复，且记录无限膨胀。
- **引入 WorkManager / 前台服务做可靠后台下载**：能力更强，但要新增原生改造、通知渠道与权限链路，超出本次范围。

## Consequences

- 恢复的任务从头下载，中断前进度对应的流量作废（无续传）。
- 队列状态与磁盘真实内容可能短暂不一致（例如用户手动删掉文件后任务仍在队列中）：以任务重下为准。
- 持久化写入必须节流，否则下载进度回调会造成高频写盘；只在状态跃迁（入队 / 开始 / 失败 / 完成）时强制落盘。
- 若未来升级 targetSdk 走 SAF/分区存储，恢复前的"目录可写"检查需要同步改造（[docs/download-metadata-plan.md](../download-metadata-plan.md) 已列为非目标）。
