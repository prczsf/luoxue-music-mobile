# ADR 0007: 内容屏蔽复用「不喜欢」规则，不新建独立黑名单

## Status

Accepted

## Context

车载场景的核心诉求是「别让我被动听到某人 / 某类歌」：开车时不能分心挑歌，遇到讨厌的歌手只想让它永远别再自动播到；但用户也不会为此删掉那张 900 首的歌单。所以需要的是**播放期过滤**，不是删除（列表即用户数据，见 [ADR 0006](0006-unplayable-music-handling.md)）。

仓库里已经有一台几乎同构的机器：「不喜欢」（storage key `@dislike_list`）。

- 数据：一个字符串，每行一条规则
- 持久化：`src/utils/data.ts`
- 事件：`dislike_event`（`dislike_music_add` / `dislike_music_overwrite` / `dislike_changed`）
- store：`src/store/dislikeList/{state,action,hook}.ts`
- 跨端同步：`src/plugins/sync/dislikeEvent.ts` 上传的就是这个字符串 + md5
- 播放过滤：`src/core/player/utils.ts` 的 `filterMusicList`
- 入口：歌曲菜单、设置页

代价对比：

| 方案 | 工作量 | 结构影响 |
| --- | --- | --- |
| A 新建独立黑名单 | 持久化 / 事件 / store / 同步 / 过滤 / 设置页 ≈ 8 文件、约 250 行 | 设置页并排两张相似卡片，用户分不清「不喜欢」与「屏蔽」 |
| B 扩展「不喜欢」 | 解析器 + 匹配器 + 入口 | 同步协议零改动（还是那个字符串 + md5），跨端立即共享 |

选 B。

## Decision

### 1. 屏蔽 = 往「不喜欢」规则里加一条

不新增 storage key、不新增事件、不改同步协议。`core/dislikeList.ts` 的 `addDislikeSinger(singers)` 复用既有 `dislike_music_add`，持久化与跨端同步免费获得。

### 2. 一套规则、四种写法

| 写法 | 语义 | 匹配 | 产生方式 |
| --- | --- | --- | --- |
| `歌名@歌手` | 单曲 | 歌名全等 && 歌手全等 | 歌曲菜单「不喜欢」 |
| `歌名` | 单曲 | 歌名全等 | 同上（歌手为空时） |
| `@歌手`（≥2 字） | 歌手 | 歌手字段**包含** | 「屏蔽该歌手」 |
| `@歌手`（1 字） | 歌手 | 降级为全等 | 兼容旧数据 |
| `~关键词`（≥2 字） | 歌名关键词 | 歌名**包含** | 设置页关键词墙 |
| `~关键词`（1 字） | 单曲 | 降级为歌名全等 | 防误伤 |

合唱曲靠「包含」自动命中（`周杰伦、费玉清` 被 `@周杰伦` 屏蔽）；「屏蔽该歌手」入口额外用 `utils/singer.ts` 的 `splitSingers` 把合唱拆成多个歌手逐个写入，因为用户点的是「这个歌手」，不是「这个组合」。

**≥2 字阈值**（`MIN_KEYWORD_LEN`）：单字规则若启用包含会命中半个曲库（`@李`、`~版`），因此过短一律降级为全等——这保证任何旧数据都不会因为新语义而突然炸开。

### 3. 匹配收敛到唯一一处

`src/utils/dislikeMatch.ts` 的 `hasDislikeFor(info, musicInfo)` 是唯一的匹配入口，`store/dislikeList/action.ts` 的 `hasDislike` 与 `core/player/utils.ts` 的播放过滤都调它。此前两份独立实现（一份在 store、一份在 player）是漂移隐患，已删除。

### 4. 阻断点在播放期与漫游窗口，不在用户列表

- 列表播放：`filterMusicList` 按规则算出**有效候选集**，`playNext / playPrev` 直接在候选集里定位，不是「跳过一首再跳过一首」——因此连续命中不会引发连跳卡顿或请求风暴。
- 随心漫游：`conveyor.dropExcludedMusic()` 在窗口内剔除命中歌（跳过 `playIndex`，遵守 ADR 0003「当前播放歌永远在窗口内」），补位走既有 `backfill`。
- 全部命中时给一次 toast 并停止，不会空转（avoid 死循环）。
- 任何路径都不调用 `removeListMusics`。

### 5. 手动点播不被拦截（与需求文档的一处刻意偏离）

需求文档要求「手动点播命中屏蔽 → 轻提示 + 自动跳下一首有效歌」。本实现不拦截：**用户明确点下的歌照常播放**，只有自动流转（下一首 / 漫游抽样 / 整单播放）才过滤。

理由：用户显式操作是最高优先级意图，静默跳走会被当成 bug；车机上尤其致命——屏幕上的歌没播，用户无法读提示，只会觉得播放器坏了。屏蔽的产品目标是「别让我被动听到」，不是「禁止我点开」。

若后续要提升可见性，正确的做法是在列表里给命中项加「已屏蔽」标记（只读匹配结果，不动数据），而不是拒绝播放。

### 6. 界面不暴露语法

`@` / `~` 只存在于存储文本。设置页是三组 Tag 墙（单曲 / 歌手 / 歌名关键词），输入框本身表达类型，`@`/`~` 由 `buildSingerRule` / `buildNameKeywordRule` 内部拼接；语法说明只留在「手动编辑规则」弹窗里。

## Consequences

- 同步免费：手机端写入 `@周杰伦`，桌面端同步拿到的是同一条规则；桌面端升级到同一解析器后立即按包含匹配生效。
- 桌面端未升级时的已知降级：旧解析器把 `@周杰伦` 按全等处理（独唱仍被屏蔽、合唱失效），把 `~live` 当歌名规则（无害无效）。
- 语法被「一行两段、`@` 分隔」这个老格式锁住：新增维度只能继续占用前缀字符（本次用了 `~`），名字里真的含 `@` 必须写 `#`（`SPLIT_CHAR.DISLIKE_NAME_ALIAS`），一行出现 2 个以上 `@` 时只取前两段。
- 一份名单混多种语义，规则数统计与 UI 分组必须随语义同步演进，否则用户看到的数字会解释不通。
- 「屏蔽」的承诺边界是「自动播放时听不到」；设置页文案必须按这个边界写，不能承诺「点了也播不了」。
- 设置页那张卡片从此承担两个职责（单曲不喜欢 + 歌手/关键词屏蔽），文案要持续压住「零语法」这条线。
